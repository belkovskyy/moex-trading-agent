# moex-ai-agent: как устроены признаки, таргет и обучение

Код в `src/moex_agent/`. Описание, без правок.

Кто за что отвечает:

| файл | роль |
|---|---|
| `ml_features.py` | единственный источник правды по набору признаков (train и inference) |
| `ml_offline_dataset.py` | сборка обучающего датасета из истории (ALGOPACK API / локальный parquet / ISS) |
| `ml_data.py` | онлайн-сборщик того же датасета в проде |
| `ml_baseline.py` | обучение LightGBM + walk-forward CV |
| `ml_filter.py` | инференс: загрузка .joblib, `predict_proba` |
| `backtest.py` | симуляция; модель только применяется |
| `algopack_local.py` | подстановка локальных parquet вместо API |

## 1. Признаки

`ml_features.py` — 30 колонок, порядок фиксирован в `FEATURE_COLUMNS`:

- **BASE, 14** — `price`, `rsi`, `macd`, `macd_signal`, `bollinger_low/mid/high`, `atr_pct`,
  `volume_ratio`, `trade_imbalance`, `order_imbalance`, `book_imbalance`, `book_spread_pct`, `super_volume`.
- **DERIVED, 6** — арифметика от BASE, истории не требует: `rsi_centered`, `macd_diff`, `macd_diff_norm`,
  `bb_position`, `bb_width_pct`, `price_to_bb_low`.
- **TIME, 5** — из `feature_ts` в MSK: `hour_sin`, `hour_cos`, `is_morning_session`, `is_main_session`,
  `is_evening_session`.
- **MACRO, 5** — `imoex_return_60m`, `imoex_return_4h`, `sector_return_60m`, `corr_price_imoex_60`,
  `rel_strength_vs_imoex`.

Отдельно выделена группа `MICROSTRUCTURE_FEATURE_COLUMNS` (5 штук: `trade_imbalance`, `order_imbalance`,
`book_imbalance`, `book_spread_pct`, `super_volume`) — флаг `--no-microstructure` в `ml_baseline.py` её выкидывает,
чтобы измерить вклад платной подписки.

Откуда берутся:
- индикаторы — `indicators.build_features(history, ...)`, где `history = candles[idx+1-60 : idx+1]`
  (`ml_offline_dataset.py:492-509`), то есть только прошлое и текущий бар;
- микроструктура — `_build_super_features(history[-1].ts, ...)` (`ml_offline_dataset.py:210`), берёт
  последнюю строку tradestats/orderstats/obstats с меткой **≤ ts текущего бара** (`bisect_right - 1`);
- макро — `macro_data.compute_macro_features(ts=...)`, все окна заканчиваются на `ts`, поиск через
  `latest_before` — заглядывания вперёд нет.

NaN не бывает: `_safe()` подменяет любое непарсящееся значение на `0.0`. Отличить «признака нет» от «признак равен
нулю» модель не может.

## 2. Таргет и горизонт

Два режима, `--target-mode` (`ml_offline_dataset.py`):

1. **`triple_barrier`** — по умолчанию и рекомендованный. `triple_barrier_label()` (строка 354) идёт вперёд от
   `entry_idx+1` до `entry_idx+horizon`, смотрит `high`/`low` каждой свечи и возвращает, какой барьер сработал первым:
   верхний `+1.2%` (`--barrier-up 0.012`), нижний `−0.8%` (`--barrier-down 0.008`), иначе `flat` по таймауту.
   Если оба барьера в одной свече — направление угадывается по `close` vs `open`.
2. **`return`** (legacy) — `future = candles[idx + horizon_steps]`, метка по знаку доходности с порогом
   ±0.15% (`ml_data.TARGET_UP_THRESHOLD`).

**Горизонт**: `--horizon-steps`, по умолчанию `settings.ml_label_horizon_steps = 3` бара.
Длина бара — `CANDLE_PERIOD`, по умолчанию `10min`, но локальные parquet ALGOPACK пятиминутные,
и `algopack_local._to_candle` строит свечи прямо из строк tradestats без ресемпла. То есть на локальных
данных горизонт фактически **3 × 5 мин = 15 минут**, а не 30.

**Задача модели**: `--task binary_up` (по умолчанию) — `up` vs `not_up`, то есть P(сработает тейк раньше стопа).
Есть зеркальный `binary_down` для шорт-фильтра и `multiclass`.

В проде тот же таргет собирает `ml_data.MLDataCollector`: держит очередь из `horizon_steps` наблюдений и,
когда приходит `horizon_steps+1`-е, пишет строку с forward-return — то есть онлайн-версия использует только
режим `return`, без барьеров.

**Фильтр строк**: `--entry-only` включён по умолчанию (`ml_baseline.py:56`) — обучение идёт только по строкам,
где эвристическая стратегия уже сказала `buy`. Модель учится не «куда пойдёт рынок», а «какие из сигналов
стратегии стоит пропускать».

**Веса**: `weights = 1 / horizon_steps` (`ml_baseline.py:145`) — облегчённая uniqueness-поправка Лопеса де Прадо.
При triple-barrier горизонт у строк разный (ранние касания), так что вес реально работает.

## 3. Разбиение train/test и embargo

Всё в `ml_baseline.py`.

- Строки грузятся из jsonl и сортируются **глобально по `feature_ts`** (строка 101). Тикеры перемешаны:
  на одну метку времени приходится столько строк, сколько символов в датасете.
- **Walk-forward CV**: `_purged_walk_forward_indices()` (строка 149). `fold_size = n // (folds+1)`,
  train — расширяющийся от начала (`0 : fold_size*(k+1)`), test — следующий блок того же размера,
  между ними пропуск `embargo` строк. По умолчанию `--cv-folds 5`, `--embargo-candles 10`.
- **Финальный сплит**: `split_index = n * (1 - test_size)`, `test_size=0.20`;
  `x_train = x[:split_index]`, `x_test = x[split_index + embargo:]` (строки 292-293).
  Embargo применён и здесь.

Разрыв между train и test **есть**, но с двумя оговорками:

1. Embargo меряется **в строках, а не в барах и не во времени**. При 20 тикерах watchlist на одну временную метку
   приходится ~20 строк, поэтому `embargo=10` — это меньше одного пятиминутного бара.
2. Purge в собственном смысле нет, несмотря на название функции. Строки в **конце train**, чьё окно разметки
   (до `horizon_steps` баров вперёд, при triple-barrier — до 3 баров) заходит в тестовый блок, из train не удаляются.
   Односторонний embargo в 10 строк это окно не перекрывает.

## 4. Скейлеры и энкодеры

**Их нет.** LightGBM обучается на сырых `list[list[float]]`, без `StandardScaler`, `OneHotEncoder`,
`LabelEncoder` и `Pipeline`. Метки классов — строки `"up"/"not_up"`, их кодирует сам `LGBMClassifier`,
внутри `fit()`, то есть внутри фолда. Вопрос «fit скейлера до разбиения или внутри фолда» здесь не возникает.

Единственное место с преднормировкой во всём пакете — `memory.py:176-184` (kNN-поиск похожих сетапов):
z-score `mean`/`std` считается по **всей** загруженной выборке сразу, затем `NearestNeighbors.fit(x_norm)`.
Это не ML-фильтр и в обучении LightGBM не участвует, но нормировка там действительно глобальная.

## 5. shift(-1), rolling(center=True), .iloc[i+1]

Pandas в ML-тракте не используется вообще — всё на списках и `bisect`. Прямых `shift(-1)`, `rolling(center=True)`,
`.iloc[i+1]` в коде нет (`grep` по `src/`, `tests/` — 0 совпадений).

Их функциональные аналоги — и все они относятся к **таргету**, не к признакам:

- `future = candles[idx + args.horizon_steps]` — `ml_offline_dataset.py:524`, режим `return`;
- цикл `for j in range(entry_idx + 1, last_idx + 1)` в `triple_barrier_label` — `ml_offline_dataset.py:372`;
- граница `last_index = len(candles) - horizon_steps - 1` (строка 479) — хвост, где разметка не помещается,
  в датасет не попадает.

Признаки заглядывания вперёд не содержат: и индикаторы, и микроструктура, и макро читают только `ts ≤ текущий бар`.

Два момента на границе, которые стоит знать:

- `_latest_before` использует `bisect_right(times, ts) - 1`, то есть **включает** строку с меткой, равной метке бара.
  Свеча в `algopack_local._to_candle` строится из той же строки tradestats. Значит признак и цена входа относятся
  к одному и тому же уже закрытому бару — само по себе непротиворечиво, но исполнение по этому бару должно быть
  на следующем.
- `backtest.py` исполняет вход по `features.price * (1 ± slip)` (строки 577, 655), где `features.price` —
  close того самого бара, на котором посчитан сигнал. То есть сделка происходит по цене закрытия бара,
  чья агрегированная статистика уже использована в признаках.

Отдельно: `backtest._compute_per_symbol_atr_stops` (строка 245) считает медианный `atr_pct` **по всему
загруженному датасету**, включая будущее относительно каждой сделки, и из него выводит размер стопа.
Это не утечка в модель, но параметр симуляции подобран с использованием всей истории.

## 6. Переобучается ли модель в walk-forward

- **В CV — да.** В каждом фолде вызывается `_train_lightgbm(x_tr, y_tr, w_tr)` заново
  (`ml_baseline.py:276`), с нуля, на расширяющемся окне. Это только оценка; модели фолдов не сохраняются,
  в `meta.json` уходят лишь их метрики (`cv_metrics`).
- **Отгружаемая модель — обучается один раз**, на `x[:split_index]`, то есть на первых 80% истории
  (`ml_baseline.py:299`), и сохраняется в `.joblib` + `.meta.json`.
- **Бэктест не переобучает ничего.** `backtest.py:1118-1127` один раз грузит `.joblib`
  (`MLBuyFilter.load`) и прогоняет через него всю симуляцию. Скользящего переобучения по окнам нет.
- В проде та же модель грузится из `ML_MODEL_PATH` (`lgbm_buy_filter_v5.joblib`) и
  `ML_SHORT_MODEL_PATH` (`lgbm_short_filter_v2.joblib`), порог входа `ML_MIN_UP_PROBABILITY = 0.58`.

Гиперпараметры фиксированы в коде (`ml_baseline.py:180-203`): `n_estimators=500`, `learning_rate=0.03`,
`num_leaves=31`, `min_data_in_leaf=40`, `subsample/colsample=0.85`, `reg_alpha=reg_lambda=0.1`,
`class_weight="balanced"`, `random_state=42`. Early stopping не используется, валидационного набора внутри
`fit()` нет.

## 8. Обучающий датасет — замер по факту

`data/logs/ml_dataset_v2.jsonl`, 1.9 ГБ, полный проход:

- **1 639 110 строк, 20 тикеров, 2023-01-03 … 2026-07-01.** Дублей `(symbol, feature_ts)` — **0**.
- Строк по бумагам ровно: GAZP 85 956, SBER 85 938, LKOH 85 938 … X5 43 075, YDEX 52 947
  (последние два — с дат листинга).
- `signal_action`: hold 866 293, buy 601 216, sell 171 601. В обучение по `--entry-only` идут
  только 601 216 строк с `buy` — это и есть `rows_total` в мета-файле.
- Метки на обучающем срезе: flat 574 268, down 21 345, **up 5 603 — 0.93%**. Класс, который модель
  предсказывает, встречается меньше чем в одном проценте строк. Балансировка — только
  `class_weight="balanced"` внутри LightGBM.

**Источник свечей — MOEX ISS, не ALGOPACK.** Режим `--iss` берёт свечи и макро с
`iss.moex.com` без токена, а локальный parquet используется только для микроструктуры.
Поэтому отсутствие SBER/LKOH в локальной выгрузке ALGOPACK на обучение не влияет.

**ISS-цены скорректированы на сплиты, объёмы — нет.** Проверено на VTBR: в ALGOPACK
последний бар 08.07.2024 стоит 0.01993, первый 15.07.2024 — 99.98 (×5016.6). В датасете тот же
VTBR 01.07.2024 идёт по 105.8, разрывов цены в июле 2024 нет вообще, индикаторы на 15.07 нормальные
(`bollinger_mid` 99.8, `rsi` 55.7). Но `volume_ratio` на 15.07 падает до **0.00025–0.012** и
возвращается к ~1.3 только на следующий день: средняя за окно считается по досплитным объёмам
в штуках. То есть сплит портит не цену, а один торговый день признака `volume_ratio` — ~80 баров.

**Заполнение микроструктуры в датасете** (доля строк с ненулевым значением):

| признак | `ml_dataset_v2` (20 бумаг) | `ml_dataset_micro7` (7 бумаг) |
|---|---|---|
| `order_imbalance` | **0.00%** | **0.00%** |
| `trade_imbalance` | 36.4% | 99.3% |
| `super_volume` | 36.7% | 100.0% |
| `book_imbalance` | 41.7% | 41.8% |
| `book_spread_pct` | 42.4% | 42.7% |

`order_imbalance` — константа `0.0` во всём датасете: `orderstats` кончается в январе 2021,
а окно сборки начинается с 2023-01, и `_in_window` отбрасывает эти строки целиком, после чего
`_safe()` подставляет ноль. Константный признак LightGBM просто не использует (0 сплитов, importance 0),
так что вреда нет — но и информации в нём нет.

Опаснее `book_imbalance` и `trade_imbalance`: там `0.0` означает и «данных нет», и «баланс».
Модель может разделять по такому признаку не рынок, а принадлежность бумаги к семёрке с микроструктурой.
В боевых моделях v5 этой проблемы нет — они на 25 признаках без микроструктуры.
